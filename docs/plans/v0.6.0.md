# v0.6.0 implementation plan: government-backed tax and invoice workflows

Status: implemented for the 0.6.0 release; original design retained below.

The delivered API and commands are documented in [the compliance guide](../compliance/README.md). The implementation includes order accounting, selected invoice checks, financial partial-credit drafts, SQLite persistence, source checks, locks, CI cases and React/Next.js examples. The `rules diff` input is a candidate **configuration**, including its rule pack.

Delivery boundaries: credits remain financial drafts requiring statutory review; document signing, IRP submission and statutory credit-note formatting are external. The core is tested in Node and Chromium; Electron/Hermes integration and the proposed independent new-developer usability trial remain unverified. The 15-minute onboarding figure below is a target, not a measured claim. Initial legal checks are limited to the reviewed provisions listed in [source coverage](../compliance/sources.md), including the documented CBIC retrieval limitation.
Prepared: 2026-09-09. Baseline: glocon 0.5.0.

## Release outcome

A JavaScript/TypeScript developer should be able to configure their business and reviewed product treatments once, calculate an order, produce a validated invoice draft, handle a partial credit, and run regression checks against the same rules in CI.

The flagship workflow is **business facts → reviewed tax treatment → order calculation → invoice validation → credit/correction → reproducible evidence**. Keep the existing country count (India, United States, Japan). Government requirements become executable checks where they can be expressed reliably. Unknown legal/business decisions remain explicit questions with sources and consequences.

This release prioritizes tax and invoicing. The shared requirement model also improves the existing privacy/children's-data plans, but a consent platform, deletion orchestration, and a new authentication system are separate releases.

## What exists and what changes

The current `src/tax.ts` calculates tax on a caller-classified aggregate amount and supports a small caller-managed rate registry. Callers handle order lines, rate grouping, invoices, and persistence. `src/laws.ts` provides selected boolean applicability questions, source-linked tasks, and latest review records. A different query date flags every relevant source for review; that is not change detection.

| Current capability | 0.6.0 deliverable |
| --- | --- |
| Supply a rate and amount for each calculation | Reuse reviewed product treatments, registrations, and dated rules across orders |
| Engineering checklist | Field-level validation with rule ID, condition, source, and suggested fix |
| Aggregate tax arithmetic | Order lines, mixed rates, discounts, rounding, and reconciled totals |
| No invoice workflow | Typed invoice drafts, validation, and printable HTML/JSON |
| No credit workflow | Credit-note drafts tied to original amounts and rule snapshots |
| Latest manual review assertion | Versioned decisions, implementation evidence, and explicit verification status |
| Source date mismatch | Separate effective dates, review deadlines, and detected document changes |

## 1. Configure the business once

Proposed CLI: `glocon compliance init`.

Ask only questions relevant to the selected operating model. Support interactive setup and a documented JSON input for CI. Generate `glocon.compliance.json`, its editor schema, a reviewed product-catalog template, example transactions, and a Node/Next.js integration example. Preserve existing files on repeat runs.

Collect business establishments, relevant jurisdictions, registration status, invoice identity, document numbering policy, B2B/B2C transaction categories, supported products, and the evidence behind tax treatments. Separate seller location, customer location, and legally relevant supply/sourcing decisions. Currency, language, or the buyer's country must not determine governing tax law by themselves.

Product treatment records contain stable IDs, classification/taxability decisions, source references, jurisdiction, effective dates, reviewer, review date, and reasons for exemptions or exclusions. A missing classification is not a zero rate. Reuse reviewed answers; ask again only when their scope, inputs, or rule revision changes.

## 2. Ship an order-level tax engine

Proposed import: `glocon/compliance`; retain the existing `glocon/tax` arithmetic API unchanged.

Add pure functions for line calculations, rate grouping, tax-inclusive/exclusive pricing, supported line/order discounts, shipping as an explicitly classified charge, and deterministic allocation of minor-unit remainders. Represent money as decimal strings/minor units. Keep exempt, zero-rated, and out-of-scope treatments distinct.

Resolve rules using transaction date, jurisdiction, registration context, and product treatment. Ambiguous or missing matches return `needs-context` with typed questions. Unsupported supply patterns return `unsupported`. Neither can produce an authoritative invoice. A successful calculation includes its treatment source and rule revision, not merely totals.

Proposed result union: `ready | needs-context | unsupported | invalid`. A ready result means the configured calculation was evaluated successfully; it is not a statement that the business complies with every law.

Use a `TaxProvider` interface for application-managed determinations or future external services. Ship a working adapter for versioned, reviewed local rules. Do not make the default workflow depend on a paid provider or imply that a generic adapter supplies nationwide tax data.

## 3. Make invoice requirements executable

Provide `validateInvoice`, `createInvoiceDraft`, and `createCreditNoteDraft`, plus structured JSON and escaped printable HTML. PDF generation through the existing optional browser tooling can follow after the core workflow passes. Draft generation is distinct from document issuance and government registration.

Validation errors should identify a field, why it matters, its applicability condition, and a source:

```text
IN-GST-INVOICE-PLACE-OF-SUPPLY
Field: transaction.placeOfSupply
Required by the selected inter-state invoice profile.
Action: supply the reviewed place-of-supply value.
Source: CBIC Rule 46(n)
```

India's Rule 46 specifies tax-invoice particulars, and CBIC's place-of-supply circular explains the inter-state invoice requirement. These are concrete candidates for conditional schema checks, subject to the current amendments and special invoice provisions. [CBIC Rule 46](https://taxinformation.cbic.gov.in/content-page/explore-rules/1000136/1000001), [CBIC circular 90/09/2019-GST](https://cbic-gst.gov.in/pdf/circular-cgst-90.pdf).

Credit drafts must reference the original immutable calculation snapshot, allocate amounts deterministically, and never exceed remaining refundable quantities/tax. Government-specific credit eligibility, dates, and required particulars need their own sourced rules; financial reversal arithmetic alone cannot establish eligibility.

Supply a transactional storage contract and one working SQLite server example for atomic invoice numbering, idempotency, and cumulative credit limits. Keep storage optional and out of the browser bundle. The core cannot promise uniqueness or prevent concurrent over-refunds without persistent atomic operations. Preserve issued documents and make corrections through linked documents.

## 4. Implement precise jurisdiction profiles

| Profile | Initial executable scope | Decisions that remain explicit |
| --- | --- | --- |
| India GST | Selected ordinary domestic invoice fields; reviewed intra/inter-state treatment; CGST + SGST/UTGST or IGST reconciliation | Registration, classification/rate, place of supply, exemptions, special supplies, e-invoice applicability |
| Japan consumption tax | Qualified-invoice fields for the selected document type; reviewed rate categories; aggregation and rounding by rate | Registration, reduced-rate eligibility, special document exceptions, transaction treatment |
| United States | General engine with caller/provider-supplied dated jurisdiction decisions; a clearly labelled California reference profile | Nexus, product taxability, sourcing, exemptions, all other states' requirements |

Japan requires rounding once per rate per qualified invoice, rather than summing individually rounded item taxes. Build that grouping into the new engine instead of leaving it to every caller. Its invoice guidance also specifies registration and rate-grouped information. [NTA rounding guidance](https://www.nta.go.jp/taxes/shiraberu/taxanswer/shohi/6371.htm), [NTA invoice particulars](https://www.nta.go.jp/taxes/shiraberu/taxanswer/shohi/6625.htm).

California explains that district taxes affect rates and that a ZIP code or mailing address alone does not always establish the correct rate. Consequently, a country or ZIP-only rate shortcut is not an acceptable default. [CDTFA rate guidance](https://cdtfa.ca.gov/taxes-and-fees/know-your-rate.htm).

India e-invoice registration is a separate IRP workflow that returns an IRN; creating a PDF or a local invoice object does not perform it. For 0.6.0, model that requirement and its evidence explicitly. Return a blocked issuance requirement when registration is required but no verified result is supplied. Live IRP submission is outside the initial release. [GSTN e-invoice overview](https://tutorial.gst.gov.in/downloads/news/pamphlet_e_invoice_overview_updated_on_17_08_2023_approved_final.pdf).

Cross-border, reverse-charge, marketplace/deemed-supplier, composition, cess, and unusual invoice cases must appear in an explicit unsupported-scenario matrix until their end-to-end behavior is implemented and sourced. Keep ordinary zero/exempt arithmetic available without presenting an unsupported legal document as valid.

## 5. Version the rules and explain every result

Introduce immutable rule-pack revisions and `glocon.compliance.lock.json`. The lock pins the exact rule pack, schema, and content digest used by a build. Store a transaction's normalized input reference, decisions, original rule revision, calculation version, and outputs so historic results can be reproduced after upgrades.

Each requirement records its jurisdiction, source/provision, reviewed scope, effective interval when established, review deadline, and machine-checkable conditions. Keep engineering interpretation distinct from source text. Track `unknown`, `applies`, and `does-not-apply` separately; keep upcoming provisions separate from currently effective provisions. Missing commencement evidence remains unresolved.

Add proposed commands:

```sh
glocon compliance explain IN-GST-INVOICE-PLACE-OF-SUPPLY
glocon compliance sources check
glocon compliance rules diff candidate-rules.json
```

Source checks are opt-in network operations against known official documents. Return `unchanged`, `changed`, `unavailable`, or `not-checked` plus retrieval time and digest. A content change triggers review; it does not automatically rewrite a rule or establish that a law changed. Failed fetches never mean unchanged. Runtime calculations remain offline and deterministic from pinned rules.

Apply the same source/version/evidence model additively to the existing government checklists. Preserve existing record APIs, but do not display an old `done` assertion as a newly verified control when its substantive requirements change. Manual review, automated field validation, external registration, and operational verification must remain separate statuses.

## 6. Make the workflow usable from apps and CI

Proposed commands, not available in 0.5.0:

```sh
glocon compliance init
glocon tax quote examples/order.json
glocon invoice validate examples/invoice.json
glocon compliance check
```

`glocon compliance check` should validate business/catalog configuration, fixture transactions, invoice outputs, pinned rules, and required review evidence. Use exit codes consistent with the existing runner: 0 configured checks passed, 1 verified violations, 2 incomplete/unsupported/setup failures. Finance checks need their own strict acceptance rules; UI baselines must not waive a missing invoice field or unresolved tax decision.

Build a working Next.js server route and React checkout example. Recalculate authoritative totals on the server from trusted catalog data; browser calculations are previews. Treat an uploaded client total or rule snapshot as untrusted. Export only the public preview configuration to clients. Use the 0.5.0 scenarios to test loading, backend failure, retry, and the displayed invoice outcome.

Keep the calculation/validation core free of Node, DOM, and React imports. Verify it in ESM, CommonJS, TypeScript, browsers, Electron, and React Native/Hermes before advertising runtime compatibility. Server-only persistence, credentials, and CLI functions use separate subpaths. If a runtime is not exercised, document that limitation rather than claiming full integration support.

## Build sequence and completion gates

1. **Rule and scope specification.** Define the supported transaction matrix and draft result types. Map every initial validator to current official provisions and amendments. Resolve uncertainty or mark the case unsupported before coding a confident default.
2. **Pure calculation core.** Implement catalog/rule selection, order arithmetic, grouping, discounts, and allocations. Test accounting invariants, mixed rates, effective-date boundaries, ambiguous matches, zero/exempt distinctions, and JPY rounding.
3. **Invoice lifecycle.** Implement conditional validation, invoice/credit drafts, rendering, evidence snapshots, and the transactional server example. Test duplicate requests, concurrency, cumulative partial credits, escaping, and immutable issued records.
4. **Developer workflow.** Implement idempotent setup, example data, explain/validate/check commands, version locking, and source review/diff reports. Keep old country, tax, laws, and UI commands working.
5. **Real integration and release.** Run the complete checkout → invoice → partial-credit workflow from a clean npm installation in Next.js and React/Vite. Verify portable-core claims separately. Publish release notes, tested tarball, and GitHub release alongside npm 0.6.0.

Required release evidence:

- Every supported profile has successful examples and deliberate violations with an official source for each legal validation.
- Every issued amount reconciles; summed credits never exceed the original under concurrent requests.
- Old invoices reproduce with their original rules after a candidate rule update.
- Missing/ambiguous treatment, unknown applicability, required missing external evidence, and unavailable sources cannot silently become a passing result.
- One new developer can reach a valid sample order/invoice in a target of 15 minutes without consulting implementation code. Measure this as a usability trial, not a current performance claim.
- Existing 0.5.0 tests, package-manager checks, and exports remain compatible. New financial behavior gets independent fixtures derived from official examples and a second arithmetic reference where appropriate.
- Current government-source review is completed for the executable profiles before publication; source retrieval alone is not that review.

## Explicit release boundaries

No new countries, universal tax classification, nationwide US rate database, income/payroll taxes, returns/remittance service, live government filing, full historical law database, or automatic legal certification. No production behavior changes from an unreviewed web scrape. Unsupported cases return actionable reasons and evidence requirements.

These boundaries make the promised supported workflow usable in production: developers get reusable implementation and verification, while the library remains honest about the business decisions and integrations it has not performed.
